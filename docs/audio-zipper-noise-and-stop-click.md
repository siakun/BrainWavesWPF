# 음량을 바꾸거나 멈출 때 나는 틱 소리 없애기

실시간으로 파형을 만드는 앱에서 음량 슬라이더를 끌면 "띠띠띠" 하는 잡음이 섞이거나, 재생을 멈추고 시작할 때 "딱" 소리가 날 때 보는 문서입니다. 원인은 소리에 닿는 값이 샘플 한 개 사이에 바뀌어 파형이 계단처럼 꺾이는 데 있습니다. 해결은 값을 바로 쓰지 않고 목표값으로 받아, 샘플마다 조금씩 그 목표로 옮겨 가게(parameter smoothing) 하는 것입니다. 정지도 출력 장치를 바로 멈추지 않고 소리를 끝까지 줄인 뒤 스트림을 끝냅니다. NAudio의 `ISampleProvider`처럼 버퍼를 직접 채우는 생성기에 해당하며, 녹음된 파일을 재생하는 경우에도 음량과 정지에는 같은 원리가 적용됩니다.

## 증상과 겉보기가 비슷한 문제

- 음량을 천천히 바꿀수록 잡음이 촘촘하게 들리고, 슬라이더를 멈추면 잡음도 멈춥니다. 바뀌는 값 하나하나가 틱 소리 하나라서, 오디오 분야에서는 지퍼 노이즈(zipper noise)라고 부릅니다.
- 재생을 멈추는 순간이나 시작하는 순간에 한 번 "딱" 소리가 납니다.

값을 바꾸지 않는데도 잡음이 끊이지 않으면 이 문서의 원인이 아닙니다. 그때는 버퍼가 제때 채워지지 않는 언더런을 의심합니다. 버퍼를 채우는 코드가 오래 걸리거나 출력 지연(latency)이 너무 짧으면, 장치가 채워지지 않은 버퍼를 재생하며 일정하게 끊깁니다.

## 원인

사인파 `x[n] = A * sin(phase[n])`에서 진폭 `A`가 샘플 한 개 사이에 `ΔA`만큼 바뀌면, 그 샘플에서 파형이 `ΔA * sin(phase)`만큼 위아래로 뜁니다. 이렇게 뛴 자리는 넓은 주파수 대역에 걸친 짧은 소리, 곧 틱 소리로 들립니다. 슬라이더는 끄는 동안 값을 잇달아 보내므로 틱 소리가 줄지어 납니다.

- 값을 버퍼를 채우기 시작할 때 한 번에 적용하면 버퍼 경계마다 계단이 생깁니다. 버퍼를 잠근 채 값을 바꾸든, 잠금 없이 바꾸든 같습니다. 문제는 한 번에 바꾸는 것이지 경쟁 상태가 아닙니다.
- 주파수는 위상을 이어서 더하면 값이 뛰지는 않습니다. 대신 기울기가 한 샘플 사이에 바뀌어 파형이 꺾이고, 주파수 차이가 클수록 꺾임이 커집니다.
- 정지할 때 출력 장치를 바로 멈추면 재생 중이던 버퍼가 그 자리에서 잘립니다. NAudio의 `WaveOutEvent.Stop`은 WinMM의 `waveOutReset`을 불러 대기 중인 버퍼를 버리므로, 0이 아닌 값에서 0으로 한 번에 떨어집니다. 이 부분은 코드 구조와 API 설명에서 도출했고 장치 출력을 녹음해 확인하지는 않았습니다.
- 처음부터 최종 음량으로 시작하면 시작하는 순간 기울기가 한 번에 생깁니다.

## 진단: 이계 차분으로 계단 찾기

귀로 듣지 않고도 생성기가 만든 샘플 배열에서 계단을 찾을 수 있습니다. 이웃한 세 샘플의 이계 차분 `|x[n+1] - 2x[n] + x[n-1]|`의 최댓값을 봅니다.

- 진폭 `A`, 각주파수 `ω = 2πf / 샘플레이트`인 부드러운 사인파에서 이 값은 `A * ω²` 이하입니다. 75 Hz, 진폭 0.16이면 약 1.8×10⁻⁵입니다.
- 진폭이 `ΔA`만큼 뛴 자리에서는 `ΔA * |sin(phase)|` 크기로 튑니다. 0.01만 뛰어도 사인파 자체 값의 수백 배입니다.

그래서 같은 조작을 주고 만든 파형에서 이 값을 "아무것도 바꾸지 않은 같은 진폭의 사인파"와 비교하면, 비슷하면 계단이 없고 몇 배 이상이면 계단이 있습니다. 생성기를 출력 장치 없이 직접 `Read`해서 측정하므로 소리를 내지 않고 반복해 확인할 수 있습니다.

이 저장소에서 슬라이더를 끄는 상황(전체 음량을 20ms마다 1%씩 10%에서 40%로)과 프리셋을 바꾸는 상황(재생 중 75/73 Hz에서 194.66/181.33 Hz로)을 50ms 버퍼 단위로 흉내 내어 잰 값은 다음과 같습니다.

| 조작 | 값을 한 번에 바꿈 | 샘플마다 옮겨 감 | 바꾸지 않은 사인파 |
|---|---|---|---|
| 음량 10%에서 40%로 | 1.2×10⁻² | 2.2×10⁻⁵ | 1.8×10⁻⁵ (40%) |
| 주파수 75 Hz에서 194.66 Hz로 | 3.4×10⁻³ | 1.5×10⁻⁴ | 1.5×10⁻⁴ (194.66 Hz) |

이 지표는 파형의 꺾임을 재는 대리 지표입니다. 들리는 잡음의 크기와 비례한다고 보지만, 청취 실험으로 대응시키지는 않았습니다.

## 해결

### 값은 목표로만 받고 샘플마다 옮긴다

소리에 닿는 값마다 "목표값"과 "지금 소리에 쓰는 값"을 따로 둡니다. UI 스레드는 목표값만 바꾸고, 버퍼를 채우는 스레드는 샘플마다 지금 값을 목표 쪽으로 조금씩 옮깁니다.

```csharp
// 목표값을 향해 rampSamples개 샘플에 걸쳐 같은 폭으로 옮겨 간다. 도중에 목표가 바뀌면 지금 값에서 다시 시작한다.
public void SetTarget(double target)
{
    if (target == _target) return;
    _target = target;
    _remaining = _rampSamples;
    _step = (target - Current) / _rampSamples;
}

public double Next()
{
    if (_remaining == 0) return Current;
    _remaining--;
    Current = _remaining == 0 ? _target : Current + _step;   // 마지막 샘플에서 정확히 목표가 된다
    return Current;
}
```

옮기는 방식은 두 가지가 흔합니다.

| 방식 | 성질 | 맞는 값 |
|---|---|---|
| 정해진 샘플 수에 걸친 직선 이동 | 정해진 시간 안에 목표에 정확히 닿습니다 | 정확한 값이 중요한 주파수, 음량 |
| 남은 거리에 비례해 다가가는 지수 이동(1차 저역 통과) | 목표 근처에서 느려져 귀에 자연스럽지만 목표에 끝내 닿지 않습니다 | 정확히 닿지 않아도 되는 음색 값. 쓰려면 가까워지면 목표값으로 맞추는 처리가 따로 필요합니다 |

바이노럴 비트는 좌우 주파수의 차이 자체가 들리는 소리라서, 주파수가 목표에 정확히 닿는 직선 이동을 골랐습니다. 이동 시간은 음량과 주파수 모두 50ms로 두었습니다. 슬라이더를 따라가는 지연이 느껴지지 않을 만큼 짧고, 위 측정에서 계단이 사라질 만큼 깁니다. 슬라이더를 끄는 동안에는 목표가 계속 바뀌어 매번 지금 값에서 다시 출발하므로, 소리는 슬라이더를 약간 늦게 매끄럽게 따라갑니다.

목표값은 잠금 안에서 바꾸고, 버퍼를 채우는 쪽은 버퍼를 시작할 때 한 번만 잠가 목표를 읽어 갑니다. 버퍼 전체를 잠근 채 채우면 그동안 UI 스레드가 값을 넣지 못하고 기다립니다. 목표가 버퍼 단위로만 반영되므로 반응은 최대 버퍼 하나만큼 늦어지지만, 그 안에서는 샘플마다 옮기므로 계단은 생기지 않습니다.

### 시작과 정지는 페이드로

재생 여부도 같은 방식의 값(0에서 1)으로 다룹니다. 시작하면 0에서 1로, 정지하면 1에서 0으로 옮기며 모든 채널에 곱합니다. 이 저장소에서는 250ms로 두었습니다. 직선 진행을 그대로 곱하면 페이드가 시작하고 끝나는 순간 음량의 변화율이 갑자기 바뀌므로, `0.5 - 0.5 * cos(π * 진행률)`로 바꿔 양 끝의 기울기를 0으로 만들었습니다.

정지는 출력 장치를 멈추지 않고 이렇게 처리합니다.

1. 생성기에 소리를 줄이라고만 알립니다. 화면은 바로 멈춘 상태로 바꿉니다.
2. 페이드가 0에 닿으면 생성기는 그 버퍼까지 채우고, 다음 `Read`에서 0을 돌려줘 스트림을 끝냅니다.
3. `WaveOutEvent`는 스트림이 끝나면 이미 채운 버퍼를 다 재생한 뒤 스스로 멈추고 `PlaybackStopped`를 보냅니다. 그때 장치를 닫습니다.

줄이는 도중 다시 재생하면 같은 장치에서 페이드 방향만 바꿉니다. 생성기가 이미 스트림을 끝냈다면 그 장치는 남은 버퍼를 마저 들려주게 놓아 두고 새 장치를 엽니다. 여기서 옛 장치를 닫으면 아직 재생 중인 페이드의 끝이 잘립니다. 앱을 끝낼 때는 기다릴 이벤트 처리 기회가 없으므로, 페이드 시간에 출력 지연을 더한 만큼 장치의 재생 상태를 확인하며 기다린 뒤 닫습니다.

`WaveOutEvent`는 자기를 만든 스레드의 `SynchronizationContext`를 잡아 두고 `PlaybackStopped`를 그쪽으로 보냅니다. UI 스레드에서 장치를 열면 정리도 UI 스레드에서 돌므로, 장치를 가리키는 필드를 잠금 없이 바꿀 수 있습니다. UI가 없는 스레드에서 열면 이 이벤트가 재생 스레드에서 오므로 따로 동기화해야 합니다.

## 대안과 한계

- **멈춘 동안 무음을 계속 흘려보내기**: 장치를 열고 닫지 않아 다시 재생할 때 빠르지만, 소리가 없어도 재생 중인 스트림이 남습니다. Windows가 이를 오디오 사용 중으로 보고 절전 진입을 막을 수 있어 쓰지 않았습니다. 이 영향은 확인하지 않았고 알려진 동작에 근거한 판단입니다.
- **출력 장치의 음량(`WaveOutEvent.Volume`)으로 조절하기**: 생성기를 고치지 않아도 되지만, 장치 쪽에서도 값이 한 번에 바뀌는지는 장치와 드라이버에 달려 있어 보장되지 않습니다. 이 저장소에서는 시도하지 않았습니다.
- **반응 지연**: 목표는 다음에 채우는 버퍼부터 반영되고, 그 버퍼는 이미 채워 둔 버퍼가 재생된 뒤에 들립니다. 이 저장소의 설정(출력 지연 100ms, 50ms 버퍼 두 개)으로 계산하면 값을 바꾼 뒤 새 값으로 옮겨 가는 소리가 들리기 시작하기까지 최대 약 0.1초, 목표에 닿기까지 이동 시간 50ms가 더 걸립니다. 측정한 값은 아닙니다. 더 빠른 반응이 필요하면 버퍼를 줄이되 언더런을 함께 확인합니다.
- **정지 지연**: 소리는 정지를 누른 뒤 페이드 시간과 출력 지연만큼 이어집니다. 화면은 바로 멈춘 상태로 바뀌므로 조작이 늦게 느껴지지는 않지만, 즉시 무음이 필요한 기능(예: 알림 소리와 겹치지 않게 끊기)에는 짧은 페이드를 따로 둡니다.

## 검증과 회귀 확인

생성기를 출력 장치 없이 직접 `Read`해서 다음을 확인했습니다.

- 위 두 조작에서 이계 차분 최댓값이 바꾸지 않은 사인파의 1.5배 이하입니다. 같은 조작을 값을 한 번에 바꾸는 방식에 주면 10배 이상이어서, 지표가 계단을 잡는다는 것도 함께 확인됩니다.
- 시작 직후 1ms 안의 최대 진폭이 거의 0이고, 250ms 뒤 최종 음량에 닿습니다.
- 정지하면 250ms에 걸쳐 0으로 줄고, 그 뒤 `Read`가 0을 돌려줍니다. 줄인 뒤에는 다시 키우라는 요청을 거절합니다.
- 정지하고 100ms 안에 다시 재생하면 스트림이 끊기지 않고 원래 음량으로 돌아오며, 그동안에도 계단이 없습니다.

실제 출력 장치는 채널 음량을 0으로 두어 소리 없이 확인했습니다. WPF 디스패처의 `SynchronizationContext`를 설정한 스레드에서 열었습니다.

- 정지하면 장치가 멈추고 닫힙니다.
- 줄이는 도중 다시 재생하면 같은 장치를 계속 씁니다.
- 스트림이 끝났지만 정지 알림이 오기 전에 다시 재생하면 새 장치를 열고, 늦게 온 옛 장치의 알림은 새 장치를 건드리지 않습니다.
- 앱 종료 경로는 페이드가 끝날 때까지 기다린 뒤 장치를 멈춥니다.

소리에 닿는 값을 새로 더하거나 이동 시간을 바꿨으면 같은 방식으로 이계 차분을 다시 잽니다. 들어서 확인할 때는 음량을 낮게 두고 슬라이더를 아주 천천히 끕니다. 계단은 값이 바뀔 때마다 하나씩 생기므로 천천히 끌수록 잘 들립니다.
