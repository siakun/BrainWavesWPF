# WPF 목록에서 손잡이로 끌어 순서 바꾸기

`ItemsControl` 목록의 항목을 손잡이로 끌어 같은 목록 안에서 순서를 바꿀 때 보는 문서입니다. 손잡이가 마우스를 붙잡고(`CaptureMouse`) 항목에 `TranslateTransform`을 걸어 포인터를 따라오게 하며, 지나친 항목은 끄는 항목의 높이만큼 비켜서게 합니다. 놓으면 ViewModel이 컬렉션 순서를 바꾸고, 화면은 놓기 직전에 그려진 자리에서 새 자리로 미끄러집니다. 항목이 세로로 쌓이는 목록(`StackPanel` 항목 패널)에서 한 목록 안의 순서만 바꾸고, 다른 목록이나 다른 창으로 옮기지 않을 때 해당합니다.

## 언제 쓰나

- 줄 전체가 버튼인 목록에 순서를 바꾸는 손잡이를 넣을 때. 손잡이를 누르거나 끌어도 줄의 버튼이 눌리면 안 됩니다.
- 여러 묶음으로 나뉜 목록에서 항목이 자기 묶음 밖으로 나가면 안 될 때.
- 놓을 자리를 끄는 동안 바로 보여 주고 싶을 때.

다른 창이나 다른 목록으로 항목을 옮겨야 하면 이 문서가 아니라 OS 드래그앤드롭(`DragDrop.DoDragDrop`)을 봅니다. 데이터를 다른 곳으로 넘기는 경로는 그쪽에만 있습니다.

## 구조 선택: OS 드래그앤드롭과 마우스 붙잡기

| 방법 | 끄는 동안 보이는 것 | 맞는 경우 |
|---|---|---|
| `DragDrop.DoDragDrop` | 커서 모양으로 놓을 수 있는지만 알려 줍니다. 놓을 자리 표시와 끄는 항목의 그림은 장식(adorner)으로 따로 그려야 합니다 | 다른 목록, 다른 창, 다른 앱으로 데이터를 넘길 때 |
| 손잡이가 마우스를 붙잡고 항목을 직접 옮김 | 항목이 포인터를 따라오고 다른 항목이 비켜서므로 놓을 자리가 그대로 보입니다 | 한 목록 안의 순서만 바꿀 때 |

이 저장소는 한 목록 안의 순서만 바꾸므로 두 번째를 골랐습니다. `DoDragDrop`으로 직접 만들어 비교하지는 않았고, 위 표의 차이는 두 방식의 구조에서 나온 판단입니다.

## 구현의 요점

### 손잡이가 줄 버튼의 클릭을 막는다

손잡이는 줄 버튼(`Button`) 안에 놓이므로, 그대로 두면 손잡이를 누른 마우스 누름이 바깥 버튼까지 올라가 클릭이 됩니다. 손잡이의 `MouseLeftButtonDown`에서 `e.Handled = true`로 표시하면 바깥 버튼은 눌리지 않습니다. 끌지 않고 눌렀다 떼기만 해도 마찬가지여야 하므로, 끌기를 시작할지 정하기 전에 먼저 표시합니다. 같은 줄 안의 별 버튼이 재생을 막는 것도 안쪽 버튼이 누름을 먼저 처리해서이며, 손잡이는 버튼이 아니라서 직접 표시합니다. 실제 마우스 입력으로 손잡이를 눌렀다 떼면 재생되지 않고, 같은 줄의 빈 곳을 누르면 재생되는 것을 함께 확인했습니다.

끌기는 포인터가 `SystemParameters.MinimumVerticalDragDistance` 이상 움직인 뒤에 시작합니다. 그 전에 떼면 아무 일도 일어나지 않습니다.

### 위치는 배치된 자리로 잰다

항목의 자리는 `VisualTreeHelper.GetOffset(container).Y`로 잽니다. 이 값은 배치(arrange)가 정한 자리이고 `RenderTransform`을 포함하지 않습니다. `TranslatePoint`는 `RenderTransform`까지 반영하므로, 끄는 동안 움직여 그린 항목에 쓰면 계산의 기준이 함께 움직입니다. 포인터 위치는 화면이나 창이 아니라 항목 패널 기준(`e.GetPosition(host)`)으로 잽니다. 그래야 스크롤로 목록이 움직여도 같은 계산이 맞습니다.

### 자리를 바꾸는 기준은 가장자리로 정한다

끄는 항목의 가운데가 이웃 항목의 가운데를 넘을 때 자리를 바꾸게 했더니, 목록 끝까지 끌어도 끝 자리로 들어가지 않았습니다. 끄는 항목을 목록 끝에서 멈추게 하면 그 자리에서 끄는 항목의 가운데가 끝 항목의 가운데와 정확히 같아져 "넘는다"는 조건이 참이 되지 않기 때문입니다. 실제로 세 항목 묶음의 첫 항목을 맨 아래까지 끌었을 때 들어갈 자리가 끝 자리가 아닌 두 번째 자리로 계산됐습니다. 끄는 항목이 끝 항목보다 키가 크면 가운데가 끝 항목의 가운데에 아예 닿지 못합니다.

내려갈 때는 끄는 항목의 아래 가장자리, 올라갈 때는 위 가장자리가 이웃 항목의 가운데를 지나면 자리를 바꾸도록 고쳤습니다. 목록 끝에 닿으면 가장자리가 끝 항목의 가운데를 반 항목만큼 넘으므로 항상 끝 자리가 됩니다.

```csharp
var top = tops[old] + offset;
var bottom = top + heights[old];
var target = old;
for (var i = 0; i < old; i++)
    if (top < tops[i] + heights[i] / 2) { target = i; break; }
for (var i = count - 1; i > old; i--)
    if (bottom > tops[i] + heights[i] / 2) { target = i; break; }
```

이 기준에서는 이웃 항목을 반쯤 덮었을 때 자리가 바뀌므로, 가운데 기준보다 반 항목 일찍 반응합니다.

### 목록 끝에서 멈추면 다른 목록으로 나가지 않는다

끄는 거리를 `[-tops[old], 마지막 항목의 아래 끝 - (tops[old] + heights[old])]` 범위로 자릅니다. 항목은 자기 목록의 위아래 끝을 넘지 못하므로, 묶음 밖으로 옮길 수 없다는 제약이 화면에서도 보입니다. 지나친 항목은 원래 자리와 들어갈 자리 사이에 있는 것만 끄는 항목의 높이만큼 위나 아래로 비켜섭니다.

### 놓을 때는 그려진 자리에서 새 자리로 미끄러뜨린다

놓는 순간 항목은 포인터 아래, 즉 새 자리와 어긋난 곳에 그려져 있습니다. 변환을 0으로 되돌리고 순서만 바꾸면 항목이 새 자리로 튑니다. 다음 순서로 처리합니다.

1. 항목마다 지금 그려진 자리(배치된 자리 + 변환 값)를 기억합니다.
2. 이동 명령을 실행합니다. ViewModel이 컬렉션 순서를 바꿉니다.
3. 모든 변환을 0으로 되돌리고 `UpdateLayout()`으로 새 순서를 배치합니다.
4. 항목마다 `기억한 자리 - 새 자리`에서 0으로 가는 애니메이션을 겁니다.

새 자리를 실제 배치에서 다시 읽으므로, ViewModel이 저장에 실패해 순서를 그대로 두면 항목은 원래 자리로 돌아갑니다. Esc나 창 전환으로 끌기를 취소할 때도 이동 명령만 건너뛰고 같은 순서를 씁니다. ViewModel이 컬렉션을 비우고 다시 채워 컨테이너를 새로 만드는 경우도 항목을 기준으로 찾으므로 같은 계산이 맞을 것으로 예상하지만, 그 경로는 실행해 보지 않았습니다.

중간에서 놓으면 항목이 남은 거리를 짧게 미끄러져 새 자리에 들어가는 것을 변환 값의 변화로 확인했습니다. 미끄러지는 동안 같은 목록에서 새로 끌기 시작하면 진행 중인 애니메이션을 지우며 항목이 튀므로, 그동안은 새 끌기를 받지 않습니다. 이 표시는 정적 컬렉션이 아니라 항목 패널에 붙인 attached property에 둡니다. 정적 컬렉션에 두면 애니메이션이 끝나기 전에 화면이 버려질 때 패널 참조가 남습니다.

### 스크롤 중에도 포인터 아래에 둔다

목록이 스크롤 영역 안에 있으면, 끄는 동안 휠이나 자동 스크롤로 목록이 움직여도 마우스 이동 이벤트는 오지 않습니다. `ScrollViewer.ScrollChanged`에서 `Mouse.GetPosition(host)`로 위치를 다시 계산하면 항목이 포인터 아래에 머뭅니다. 자동 스크롤에서는 이 계산으로 항목이 따라가는 것을 확인했습니다. 마우스를 붙잡은 동안 휠을 굴리는 경우도 스크롤이 일어나면 같은 경로를 타지만, 휠 입력 자체는 확인하지 않았습니다.

자동 스크롤은 타이머로 포인터가 스크롤 영역의 위아래 끝 근처에 있는지 보고 굴립니다. 끄는 항목이 이미 목록 끝에 닿아 더 갈 수 없는 쪽으로는 굴리지 않습니다. 굴리면 항목은 그대로인데 목록만 화면 밖으로 밀려납니다. 화면보다 긴 목록에서 첫 항목을 화면 아래 끝까지 끌고 있으면 화면이 내려가며 항목이 화면 밖에 있던 자리까지 들어가는 것을 확인했습니다.

### 끄는 동안의 모양은 상속되는 속성으로 그린다

끄는 항목의 컨테이너에 상속되는 읽기 전용 attached property(`DragReorder.IsDragging`)를 켭니다. 값이 항목 템플릿 안의 모든 요소로 상속되므로, 줄의 스타일과 손잡이의 스타일이 각자 트리거로 끄는 동안의 모양을 정합니다. 끄는 줄은 비켜서는 줄 위를 지나가므로 바탕을 채워야 아래 줄이 비쳐 보이지 않고, 컨테이너의 `Panel.ZIndex`를 올려야 다른 줄 위에 그려집니다. 마우스를 붙잡은 동안에는 포인터가 줄 밖으로 나가도 이 모양을 유지해야 하므로 `IsMouseOver`에 기대지 않습니다.

## 증상으로 원인 찾기

| 증상 | 먼저 볼 것 |
|---|---|
| 손잡이를 누르면 줄이 클릭된다 | 손잡이의 `MouseLeftButtonDown`을 처리됨으로 표시했는지. 끌지 않는 경우에도 표시해야 합니다 |
| 목록 끝까지 끌었는데 끝 자리로 들어가지 않는다 | 자리 바꿈 기준이 가운데끼리의 비교인지. 위 "가장자리" 절 |
| 놓을 때 항목이 새 자리로 튄다 | 순서를 바꾸기 전에 그려진 자리를 기억하고, 새 배치에서 그 차이만큼 되돌려 애니메이션하는지 |
| 휠을 굴리면 끄는 항목이 포인터에서 떨어진다 | 포인터를 항목 패널 기준으로 재는지, `ScrollChanged`에서 다시 계산하는지 |
| 끄는 줄 아래로 다른 줄이 비친다 | 끄는 줄의 바탕이 투명한지, `ZIndex`를 올렸는지 |

## 검증과 회귀 확인

손잡이가 줄의 클릭을 막는지는 실제 마우스 입력으로만 확인됩니다. WPF 입력 관리자에 원시 입력 보고를 직접 넣는 방법은 버튼 상태가 `Released`로 나와 줄의 버튼이 원래 눌리지 않으므로, 막혔는지 구별되지 않습니다. 실제 입력으로 끄는 방법과 주의점은 [실제 백엔드 없이 WPF 화면 상태를 그려 확인하기](wpf-ui-state-verification-without-backend.md#실제-마우스로-끌기를-확인할-때)에 있습니다.

끌기 동작을 바꿨으면 다음을 확인합니다.

- 손잡이를 눌렀다 떼면 아무 일도 일어나지 않고, 같은 줄의 다른 곳을 누르면 클릭됩니다. 대조군이 통과해야 앞의 결과를 믿을 수 있습니다.
- 첫 항목을 맨 아래까지, 끝 항목을 맨 위까지 끌면 각각 끝 자리와 첫 자리로 들어갑니다.
- 끝 항목을 목록 밖으로 끌어도 변환 값이 목록 끝에서 멈춥니다.
- 중간에서 놓으면 변환 값이 0이 아닌 값에서 0으로 줄어들고, 끝나면 미끄러지는 중 표시가 꺼집니다.
- Esc를 누르면 순서가 그대로이고 모든 변환 값이 0으로 돌아갑니다.
- 화면보다 긴 목록에서 아래 끝까지 끌고 있으면 스크롤 위치가 늘어납니다.
- 옮긴 순서가 저장되고, ViewModel을 새로 만들어도 같은 순서로 보입니다.
